# Invoice cron

`GET /api/cron/invoices` in the admin app processes completed orders whose
`invoiceStatus` is `pending` (or null). Each call snapshots up to 25 orders and
renders up to 25 queued invoices, stopping new work after four minutes. The
route has a five-minute maximum duration. Further invocations drain the backlog.

## Setup

1. Apply migration `0174_invoice_cron` through the normal database migration
   process (`pnpm --filter @jp/db migrate`). It adds the invoice queue fields,
   makes order IDs unique in invoices, and aligns invoice quantity/tax precision
   with order lines. It also includes the previously unmigrated change of order
   line `unit_quantity` to two decimal places. Existing duplicate invoice order
   IDs must be reviewed before applying the unique index; the migration does
   not delete or merge them.
2. Set `CRON_SECRET` in the admin Vercel project.
3. Create a **private** Vercel Blob store and set its read/write token as
   `INVOICE_BLOB_READ_WRITE_TOKEN`. This is separate from the public catalog
   store. Both PDF uploads and authenticated downloads use this token.
4. Configure Vercel Cron for `/api/cron/invoices` at a frequency supported by
   your plan. For example, in the admin project's `vercel.json`:

   ```json
   { "crons": [{ "path": "/api/cron/invoices", "schedule": "*/10 * * * *" }] }
   ```

Vercel supplies `Authorization: Bearer <CRON_SECRET>`. No browser session is
required. Without the secret the route returns 401; without the storage token
it returns 503. Successful responses contain `scanned`, `issued`, and `failed`
counts. Item failures return 500 after other eligible work is processed.

## Lifecycle

- One database statement saves the invoice, all invoice lines, and the order's
  `processing` marker. A unique invoice `orderId` prevents duplicates, including
  simultaneous invocations. Numbers use `INV-` followed by the order ID.
- Completed order amounts, customer/seller addresses, and line descriptions are
  copied as snapshots. No current product prices are fetched or recalculated.
  Missing shipping addresses fall back to the billing address. Payment terms
  and due dates are left unset because the current customer schema has no such
  policy.
- A database lease using `FOR UPDATE SKIP LOCKED` claims one PDF at a time.
  Leases expire after ten minutes so terminated runs can recover. PDF failures
  retry after 5, 10, 20, ... minutes, capped at six hours. Inspect `pdfAttempts`,
  `pdfError`, `pdfNextAttemptAt`, and server logs for persistent failures.
- A deterministic private blob path permits safe upload retries. Only the
  current lease owner can finalize an invoice. Invoice and order become
  `issued` together, after the PDF upload succeeds.
- The existing authenticated `/api/v1/org/orders/:id/invoice` endpoint streams
  the saved PDF, scoped to the current organization. Existing issued invoices
  without a saved PDF are not silently regenerated by this job.

This route does not send invoice emails, apply payments, or change customer
credit balances. No schedule is installed automatically.
